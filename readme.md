Запуск сканера:
===============

python3 scanner.py [-in <in_file_path>] [-out <out_file_path>] [-threads <max_cnt>] [-timeout <secs>] [-proxy <host>:<port>]

Все параметры опциональны:

<in_file_path> - путь ко входному файлу (по умолчанию scanner_input.txt). Каждая непустая строка - в одном из 3-х вариантов:

  1. a.b.c.d
     Указывает 1 IP для провеки
  2. a.b.c.d - x
     Указывает диапазон IP от a.b.c.d до a.b.c.x
  3. a.b.c.d - x.y
     Указывает диапазон IP от a.b.c.d до a.b.x.y

<out_file_path> - путь к выходному файлу, куда будут писаться IP уязвимых машин (по умолчанию scanner_output.txt)

<max_cnt> - максимальное число используемых потоков, по умолчанию 800, это соответствуеют максимальному число потоков на
    один процесс в винде. Для линукса можно указывать хоть 3000 потоков. Главное не перегрузите ваш прокси.

<secs> - таймаут подключения к IP. Слишком низкое значение может привести к пропуску машины, слишком высокое - к
    увеличению времени чека. Используйте оптимальное значение исходя из "тормознутости" вашего прокси и числа потоков.

<host>:<port> - это опциональный SOCKS5 прокси, через который будет прокидываться чек.

При проверке каждый валид, помимо записи в файл, сопровождается логом в консоль вида:

[+] 192.168.0.141 is vulnerable (2/161 checked, 14 left)

example:

python3 scanner.py -in scanner_input.txt -out scanner_output.txt -threads 100 -timeout 10



Запуск экспа:
=============

python3 exploit.py -ip <target_ip> [-port <taget_port>] [-proxy <host>:<port>] -payload <exe_or_dll_path> [-system <use_system>]

<target_ip> и <taget_port> (по умолчанию стандартный 445) задают целевую машину.

<host>:<port> - это опциональный SOCKS5 прокси, через который машина будет пробиваться.

<exe_or_dll_path> - это путь к 64-битному EXE или DLL-файлу. Пейлоад будет выполнен бесфайлово в одном из юзерских процессов,
    правила поиска которого следующие:

    1. Если найден процесс с админсиким привилегиями, то будет использоваться он
    2. Иначе если найден процесс explorer.exe с обычными правами, о будет использоваться он
    3. Иначе если найден другой процесс с обычными правами, то будет использоваться он
    4. Иначе будет использоваться любой из оставшихся юреских процессов
    5. Если юзерских процессов не найдено (мало ли), то эксп завершится с ошибкой.

<use_system> - есди не 0, то потоку, в котором стартанет пейлоад (в контектсе процесса, в который он будет загружен), будет
    присвоен токен SYSTEM. Обращаю внимание, что токен у процесса остается прежний, меняется тольк токен потока. Это означает,
    что пейлоад, нарпимер, сможет:

    - создать нового локального админа и запусть процесс от его имени
	- создать и запустить новую системную службу
	- записать что-то в виндовую директорию или в HKLM-ветку реестра
	- ...

	Однако все это будет дейстовать только в рамках начального потока, в котором начинает работу пейлоад. Если пейлоад создаст
	новый поток или процесс, то он уже будет выполняться с обычными правами (с правами процесса, в котором выполняется пейлоад).
	Потому для использования этой опции нужен особый пейлоад + она не нужна на серверах, потому что там обычно итак все из-под
	админа запущено и дополнительных телодвижений для этого не требуется.

Выполнение экспа:
=================

Эксп репортит каждый свой щаг в консоль и держит связь с ядерным шеллкодом вплоть до момента передачи им управления в
пользовательский режим. Если шеллкод задетектил какую-то ошибку (например, не смог выделить память, создать поток и т.д.), то
он отрепортит эту ошибку экспу и тот выведет ее в консоль. Так что если эксп успешно доработал до конца, то вы можете быть
уверены как минимум в том, что юзермодный загрузчик получил управление и начал процесс бесфайлового запуска пейлоада.

Параметры экспа:
================

В файле lib\cfg.py находятся параметры, которые может потребоваться поднастроить под конкретную среду или машину, хотя
они уже установлены с средние оптимальные значения:

NUM_THREADS = 12

READ_TIMEOUT = 35

NUM_THREADS - это число потоков эксплойта. Если на сервере кол-во потоков сильно больше данного значения, то могут изредка
появляться ошибки вида [-] failed to <...>. В этом случае значение NUM_THREADS необходимо увеличить. Либо наоборот, его
можно уменьшить, если меньшего значения хватает, чтобы не перенагружать прокси.

RESTORE_CRITICAL_STRUCTS = True

Указывает восстанавливать ядерные структуры, которые портит эксп, в их исходное состояние. При установке этой опции
эксп работает стабильнее, но иногда заблюдаются ошибка [-] memory read failure. При ее стабильном повторении рекомендуется
установить опцию RESTORE_CRITICAL_STRUCTS в False.

READ_TIMEOUT - таймаут операций, которые ищут значения, записанные предыдущими операциями. В большинство случаев указанного
значения хватает за глаза, но если используемый прокси кеширует соединения с таргет-машиной и т.о. закрывает их с задержкой,
то необходимые экспу callback-и могут не срабатывать вовремя, в результате это будет приводить к ошибкам чтения. Решается либо
сильным увеличением таймаута и долгим ожиданием, либо заменой прокси на другой.

Другие параметры относятся к advanced настройкам и в большинстве случаев их менять нет необходимости.

Известные проблемы:
===================

1. Наблюдались проблемы с пробивом экспа машины, на которой поднят BC. В этом случае используйте прямое подключение к машине.
2. Возможен BSOD целевой машине, если выполнение экспа было прервано и он не сумел произвести нужную очистку. Потому старайтесь
   выполнение экспа не прерывать.
3. Если через прокси машина упорно не пробивается и есть возможность подключиться по RDP к сетке, то рекомендуется на подключенную
   машину установить python 3.8 и пробить целевую машину без прокси. Вообще, рекомендуется как можно больше сократить расстояние
   от атакующего и атакуемого компьютера, это напрямую влияет на качество пробива.

Настройка DNS для nmap-сканера (s.py):
--------------------------------------

Скрипт автоматически пробует определить DNS-серверы из вывода `ipconfig /all` (Windows) или `/etc/resolv.conf` (Linux).
При необходимости используйте переменную окружения `DNS_SERVERS` (список через запятую), чтобы явно указать адреса и
избежать предупреждений вида *"Unable to determine any DNS servers"* при запуске `nmap`.

Управление шумностью поиска живых хостов (s.py):
-----------------------------------------------

Пинг-скан живых хостов запускается параллельно. Чтобы уменьшить сетевую шумность (и нагрузку на SOC/IDS), можно:

* `ALIVE_WORKERS` — ограничить число параллельных проверок (по умолчанию выбирается автоматически, макс. 512).
* `ALIVE_BATCH_DELAY` — добавить паузу (в секундах) после каждого шага обновления прогресса, чтобы разнести ICMP-запросы
  во времени.

До появления этих переменных все ICMP-пинги выполнялись последовательно в одном процессе (фактически 1 поток), поэтому
даже при большом количестве маршрутов поиск живых хостов занимал значительно больше времени.

Обе переменные задаются перед запуском `s.py`, например: `ALIVE_WORKERS=32 ALIVE_BATCH_DELAY=0.5 python3 s.py`.
